전국 경매 물건 현황판을 갱신할 시간이다. 대구권을 우선으로 본다.

**0. 준비** — 저장소를 clone 후 브랜치 `claude/network-external-site-access-9ek78q` 체크아웃(있으면 pull). `source scripts/datagokr.sh`.

**먼저 `bash scripts/daily.sh --check` 를 돌려 인증키가 보이는지 확인한다.** 출처(환경변수/파일)와 날짜만 찍고 값은 절대 찍지 않는다. 키가 없으면 CODEF(4단계)와 실거래가 수집(3단계)이 통째로 불가능하다 — **우회하지 말고, 새로 발급받으려 하지도 말고**, 그 두 단계를 건너뛴 채 나머지를 진행하고 보고 말미에 "환경변수 DATA_GO_KR_KEY / CODEF_CLIENT_ID / CODEF_CLIENT_SECRET 가 없어 건너뛰었다" 고 분명히 적는다.

**⚠ CODEF 는 2026-09-25 에 끝났다(데모 1개월·일 100회였다. 사용자는 지금 유료 전환을 못 한다).** CODEF 키가 없으면 4단계는 건너뛰는 게 정상이다. **다른 계정으로 데모를 다시 받지 마라.** 대신 기일이 지난 물건의 결과는 **4-e 색인 재확인**으로 되짚는다(무료, 네이버 검색 API).

**오늘의 실행 순서는 이것이다:**
**1단계 발굴 → `python3 scripts/build_queue.py --write` → 4-e 색인 재확인 → `bash scripts/daily.sh` → 4-c·4-d Drive 업로드 → 6단계 발행 전 검사 → 7·8단계.**
4-e 를 daily.sh 앞에 두는 이유: daily.sh 안의 dash_sync 가 4-e 가 바꾼 매각·유찰을 대시보드 갱신 파일에 담는다.
`daily.sh` 는 3~6단계의 기계적인 부분을 순서대로 돌려준다 — CODEF 대조 → apply_codef → apply_court(4-f) → mask_names → dash_sync → 실거래가 수집 → attach_rtms → screen_clean → mark_landmarks → dash_sync --auto → build_detail → build_site → build_queue --write. 순서를 바꾸지 마라. CODEF 가 용도·특이사항·유찰횟수를 새로 채우므로 시세 매칭과 선별 등급은 반드시 그 뒤여야 한다. 다만 1단계 발굴, 4-c·4-d 의 Drive 훑기·업로드, 6단계 발행 전 검사, 7·8단계는 daily.sh 가 대신해 주지 않는다.

**⚠ `build_queue.py` 는 반드시 `--write` 를 붙여라.** 없으면 화면에만 찍고 파일을 쓰지 않는 드라이런이다. 2026-09-20 에 발굴 뒤 세 번 돌렸는데 전부 드라이런이라 큐가 88건에 묶여 있었고, 그날 보고에 적은 "124건" 은 저장되지 않은 수였다. 발굴을 CODEF 앞에 두는 이유가 바로 이것이다 — 큐를 먼저 채워 두지 않으면 배치가 100건을 못 쓴다.

**1. 물건 발굴 (매일) — 대구권 먼저, 그다음 전지역 신규 시군구**

**검색 수단 (2026-09-28 바뀜).** PlayMCP 의 네이버 검색 mcp 는 2026-09-26 부터 "이용 잠시 중단" 상태다.
먼저 `python3 scripts/naver_search.py --check` 로 키를 본다. 키(NAVER API HUB: `NAVER_APIHUB_KEY_ID`·`NAVER_APIHUB_KEY`)가
있으면 **네이버 API 를 직접 부른다** — `python3 scripts/naver_search.py raw.tsv -q "<검색어>" --display 30 --start <next>`.
검색어·display·start 규칙은 아래 그대로이고, 나온 TSV 는 extract_naver.py 로 뽑은 것과 같은 꼴이라 파서에 바로 넘긴다.
키가 없을 때만 ToolSearch 로 "NaverSearch-search_webkr" 를 로드한다(MCP 서버명이 UUID로 바뀌어 있을 수 있다). "session expired" 가 오면 같은 호출을 한 번 더 한다.
둘 다 없으면 발굴·색인 재확인을 건너뛰고 보고에 적는다(다른 검색으로 대신하지 않는다).

검색어는 이 꼴로, **한 번에 한 구만**:
```
나이스옥션 대구지방법원 대구광역시 {구} 아파트 감정가 최저가 용도
niceauction 대구광역시 {구} 아파트 소재지 청구금액 경매개시일
```
여러 지역을 묶으면 정부 문서만 딸려온다.

**대구권은 하루 3페이지, 진행표대로.** 어디까지 팠는지는 `codef-queue.json` 의
`indexFrontier` 가 기억한다(2026-09-08 사용자 요청으로 하루 1→3페이지).
`order` 순서대로 구를 돌되 `exhausted:false` 인 구의 `next.A`(검색어 A) 또는
`next.B`(검색어 B) 값을 `start` 로 넘겨 **한 번에 30건(display=30)씩 3페이지**를
받는다. 한 구에서 3페이지를 다 써도 되고, 구가 끝나면 다음 구로 넘어가서
채운다. 판 페이지는 그 자리에서 `next` 를 +30 올려 적고, **다 돌아 전부
exhausted 면 맨 앞 구부터 1페이지로 되돌린다** — 색인은 매일 새 사건이
붙으므로 재순회해야 한다. 이 파일은 `scripts/build_queue.py` 가 보존하니
날아갈 걱정은 없지만, 갱신했으면 반드시 커밋해라. 기억에 의존하면 같은
페이지를 또 판다 — 2026-09-08 에 북구 4~5페이지를 안 판 채 두었다가
사용자가 사건번호 9건을 짚어 5건이 빠진 걸 알았다.

**진행표 항목에 `queryA` 가 있으면 그것이 위 템플릿을 대신한다.** 경산시·칠곡군은
경상북도인데 '대구광역시 경산시' 로 찾으면 색인이 통째로 무너진다(2026-09-20 에
총 133건에 정부 PDF·유화증권 공시·huggingface vocab.txt 만 왔다). `나이스옥션
경상북도 경산시 아파트 감정가 최저가 용도` 로는 1,162건이 정상으로 온다.
**이런 경우를 exhausted 로 잘못 닫지 마라** — 검색어가 틀린 것이지 색인이
마른 것이 아니다. 시·도 이름을 바꿔 한 번 더 확인한 뒤에 판단한다.

`start=31`, `61`, `91` … 로 넘기면 앞 페이지와 하나도 겹치지 않는다.
북구·수성구는 한 검색어당 총 1,000건이 넘는다 — 3페이지씩 파도 열흘이 걸린다.
다만 북구 A 780 이후, 동구 A 300 이후처럼 깊은 페이지는 아파트가 거의 없고
공장·대지·근린상가만 나온다(2026-09-20~21 실측 3페이지당 13~18건). 그래도
색인 앞쪽에 새 사건이 매일 붙으니 진행표는 계속 돌린다.

**결과가 무너지면 그 구는 끝난 것이다.** 정부 PDF·KRX 공시·huggingface
`vocab.txt` 가 섞이기 시작하면 더 파지 말고 `exhausted:true` 로 적고 다음
구로 넘어가라. 서구·달서구가 그랬다 — 달서구는 총 114건이라 2페이지부터
정부 문서뿐이었다.

(2026-09-16·21 의 "CODEF 100건을 남기지 마라 · 큐 200건 이상" 지시는 CODEF 가 있을 때의 것이다.
CODEF 가 끝난 지금은 큐를 채울 이유가 없다 — 아래 ①②만 하고 ③④는 건너뛴다.
새로 발굴한 물건은 법원 대조를 못 받으므로 '미확인' 으로 남는다. 그 사실을 보고에 적는다.)

순서:
① **대구권 3페이지** (위 진행표대로).
② **전지역 신규 시군구를 6곳 이상**, `sort=date` 로 1페이지씩 돈다.
   어디를 돌 것인지는 `codef-queue.json` 의 `indexFrontier.nationwide` 가 기억한다 —
   `pool`(아직 안 훑은 시군구) 에서 위에서부터 꺼내 쓰고, 쓴 곳은 `swept` 로 옮겨 적는다.
   **이게 가장 잘 나온다.** 실측(2026-09-19~21): 새 시군구는 1페이지당 신규 20건,
   이미 훑은 곳은 8건이다. 같은 곳을 다시 돌면 중복이 80% 를 넘는다.
③ 그래도 큐가 200건 미만이면 `pool` 에서 더 꺼내 계속 돈다. 6곳으로 120건이 들어온 날도 있다.
④ `pool` 이 비면 `swept` 를 앞에서부터 다시 돌리되 `start=31` 부터 판다.

검색어는 `나이스옥션 {시도} {시군구} 아파트 감정가 최저가 용도` (지원 이름을 넣으면 정부 문서만 온다).
큐가 400건을 넘으면 그날은 발굴을 쉰다. codef_batch 는 `--limit` 을 실제 호출 수로 센다(2026-09-16 수정).

**전지역 파싱의 `--region` 에는 그날 돈 시·도를 빠짐없이 넣어라** — 빠진 시·도는 '권역 아님' 으로 버려진다:
```
python3 scripts/harvest_nice.py raw.tsv --region 서울,경기,인천,부산,대전,세종,광주,울산,경북,경남,충북,충남,전북,전남,강원,제주 --since 2025 --clean --merge
```
대구권은 `--region 대구 --since 2024 --clean --merge`. 전지역은 2025년 이후 사건만.
전지역 물건도 대장 단지만 고르지 말고 아파트 전부 넣는다(사용자 지시).

수확한 검색 결과는 **손으로 정규화하지 말고** `제목<TAB>설명` 로 파일에
그대로 붙여넣은 뒤(`<b>` 태그도 그대로 둔다) 파서에 넘긴다. 대화 기록에서 뽑으려면
`python3 <스크래치패드>/extract_naver.py "<DD Mon YYYY>" raw.tsv` 가 lastBuildDate 로 그날 결과를 걸러 준다
(파일이 없으면 jsonl 에서 `"lastBuildDate"` 가 든 JSON 문자열을 찾아 title·description 을 TSV 로 쓰는 스크립트를 새로 만든다).

파서가 권역 여부·아파트 여부·주소 가림·중복을 전부 판정하고 통계를 찍는다.
**정규식을 새로 짜지 마라.** 색인 형태 셋을 합치는 규칙과 주상복합·상가
제외가 이미 들어 있고, 근거는 docs-datagokr.md 에 있다.

`--region` 권역은 대구·부산·경북·경남·서울·경기·인천·대전·세종·광주·울산·충북·충남·전북·전남·강원·제주.
`--since 2025` 로 최근 사건만, `--clean` 으로 권리 위험어가 없고 유찰 1회 이하인 것에 `screen=clean` 을 단다.
`--max-per-case` 는 기본 3이다 — 한 사건이 60호를 일괄매각하면 목록을 통째로 덮는다.
감정가 100억 초과는 자동으로 버린다(일괄매각 총액이나 색인 오류다).
색인 제목이 잘려 단지명이 잘린 물건은 `addrCut` 이 붙고 실거래 대조에서 빠진다.

발굴분은 전부 `st='미확인'` 이다. 색인에는 진행상태가 없고 2021~2023년 사건이
흔히 섞여 있어 이미 끝났을 가능성이 크다. **진행중으로 추정하지 마라.**

경매알리미(auctionmsg.com)도 여전히 쓸 만하다 — 진행상태·유찰횟수가 스니펫에
직접 나오는 유일한 출처다. 다만 **제목의 금액은 최저매각가격이고 유효숫자
2자리로 반올림돼 있다**(8.5백=850만, 2.6억=2억6천만). 그건 `mnApprox: true` 를
켜서 넣어라. 화면에 `≈` 가 붙는다.

**색인끼리 값이 다르면 그 값은 싣지 마라.** 2025타경1239 한 건에 대해
유찰이 0회·2회, 최저가가 3.05억·2.1억·4.3억으로 갈렸다. 어느 쪽이 현재인지
색인만으로는 알 수 없다. 일치하는 것만 싣고 나머지는 비운 채 CODEF 큐로 넘겨라.

**옮겨 적은 금액은 저감 계단으로 검산해라.** 감정가·최저가가 둘 다 있으면
최저가÷감정가가 0.8ⁿ 또는 0.7ⁿ 에 정확히 떨어져야 한다. 한 자리만 잘못
옮겨도 어긋나므로 전사 검증으로 이만한 게 없다.

**2. 구조화 (매일)** — 저장소 모듈을 그대로 쓴다. 정규식을 새로 짜지 마라.
`scripts/parse_auction.py` → `split_case` / `split_addr` / `uid`
`scripts/auction_taxonomy.py` → `classify` / `special_rights`
키는 `(ct, caNo, ino)` 복합. 같은 사건의 다른 물건을 합치지 마라.
**출처가 물건종별을 명시했으면 `classify()` 에 넘기지 말고 직접 매핑하라.** classify 는 모르는 값을 아파트로 추정해버린다.

**3. 국토교통부 실거래가 (매일)** — **손으로 매칭하지 마라. 스크립트가 있다.**

```
python3 scripts/attach_rtms.py        # data.json·onbid.json 에 mk 를 얹는다
```

**data.json 을 다시 만들거나 물건을 넣은 뒤에는 반드시 이걸 돌려라.**
안 돌리면 시세가 통째로 사라진다. 끝나면 매칭 통계가 찍힌다(지번 N ·
단지명 N · 미매칭 N). 붙은 건수가 지난번보다 크게 줄었으면 주소 표기가
바뀐 것이니 보고에 적어라.

원본 시세는 `data/rtms.json` 이다. **`gen` 날짜가 7일 넘게 지났으면** 다시 모은다:

```
python3 scripts/fetch_rtms.py --months 12 --jobs 6    # 42개 시군구 1,008콜, 25~35분
```

일 한도가 10,000건이라 여유롭지만 매일 돌릴 이유는 없다. 실거래가는 월 단위로 쌓인다.
백그라운드로 돌리고 기다려라. **끝날 때까지 커밋하지 마라** — 중간에 커밋하면
시세가 안 붙고 선별 등급도 안 매겨진 data.json 이 들어간다.

매칭 규칙(지번 우선, 읍·면 접두어, 도로명 괄호, 이름 접미어 한정, 법정동 교차검증)은
전부 `scripts/attach_rtms.py` 안에 있고 근거는 docs-datagokr.md 에 적혀 있다.
**규칙을 느슨하게 풀지 마라.** 풀면 엉뚱한 단지의 시세가 붙는다 —
`태전3차우방타운` 이 `우방타운` 에 붙는 식이다. 틀린 시세는 없는 시세보다 나쁘다.
구 이름은 시·도를 넘어 겹치므로(대구 남구/부산 남구) 겹치는 이름에서는 시·도까지
대조한다. 다만 보드의 `r` 은 시·도가 아니라 **권역**이라(경산시가 `r='대구'`)
늘 대조하면 그 물건들이 떨어져 나간다 — 이 예외를 없애지 마라.

`mk.deep`(감정가 30% 아래로 내려온 물건)과 `mk.arGuess`(면적을 몰라 단지 대표
평형으로 대신함) 표시를 화면에서 지우지 마라. 둘 다 그대로 읽으면 오해를 부르는
숫자에 붙는 경고다. **`arGuess` 인 물건에는 `gap`(시세 대비 %)을 만들지 마라** —
60㎡ 중앙값에 84㎡ 최저가를 나눠 '시세의 147%' 가 나오고, 화면에서는 구분되지 않는다.
전세가율도 같은 계열의 경고를 붙여 뒀다(`jeonWarn`) — 전세 표본이 3건 미만이거나
비율이 100% 를 넘으면 두 중앙값이 비교 가능한 값이 아니다. 이 경고를 지우지 마라.

**4. CODEF 대법원 원본 검증 — 2026-09-25 종료. 키가 다시 생겼을 때만**
`codef_env` 로 상태 확인. 자격증명이 없으면 조용히 건너뛰고 보고 말미에 한 줄만 남긴다.

**한도가 두 개다. 절대 올리지 마라.**
- 일일 `CODEF_MAX_DAILY` 100건 — `codef_daily_status` 로 확인. **KST 자정 기준**으로 초기화된다.
- 주간 `CODEF_MAX_CALLS` 15건 (정식만)

스크립트가 알아서 막는다. exit 4 = 일일 한도, exit 3 = 주간 예산, exit 2 = 검증 미완료.
**한도에 걸리면 즉시 중단하고 남은 건은 다음 실행으로 넘겨라.** 재시도로 소진하지 마라. 서버가 CF-00012 를 주면 그날은 끝이다.

조회는 `python3 scripts/codef_batch.py --limit 100` 이 큐를 훑어 `/tmp/na/raw` 에 받아둔다. **사건 단위로 한 번만 부른다** — CODEF 는 사건 하나에 물건 목록을 통째로 주므로 물건번호마다 부르면 한도를 몇 배로 태운다. 서버가 CF-00012 를 주면 파일을 지우고 즉시 멈춘다(우리 카운터와 서버 카운터가 어긋난 적이 있다). 받은 뒤 `python3 scripts/apply_codef.py /tmp/na/raw` → `python3 scripts/mask_names.py`.

**조회 순서는 저장소의 `codef-queue.json` 을 따른다.** 우선순위대로 정렬돼 있고 대구권이 앞에 온다. 다 돌았거나 새 물건이 생겼으면 같은 형식으로 다시 써서 커밋해라 — 어디까지 했는지를 기억에 의존하면 같은 건을 다시 부르거나 빠뜨린다.
이미 `verified:true` 인 물건은 상태가 바뀔 사유가 없으면 다시 부르지 마라.

**큐는 비어도 안 되고 넘쳐도 안 된다.** 발굴은 싸고 원본 검증은 하루 100건이다.
큐가 400건(4일치)을 넘으면 그날은 새 발굴을 건너뛰고 큐만 소진하고, **큐가 200건 미만이면
1단계의 확대 순서대로 채운다.** 배치가 100건을 다 못 쓴 채 끝났으면
(daily.sh 요약의 CODEF 건수와 `codef_daily_status` 를 본다) 발굴을 더 하고
`build_queue.py --write` 를 다시 돌린 뒤 같은 날 배치를 한 번 더 돌린다.

받은 값 반영:
- `resFinalResult` 가 배당종결·취하·기각·각하·정지 → `st='종료'`, `note` 에 종국결과와 종료일
- `resProductList[]` 의 `resValuationAmt`(감정가) / `resAmount`(최저가) / `resUseType`(용도, `utGuess=false`) / `resState`
- `resState` 에 매각허가·대금납부·배당이 있으면 `st='매각'`
- `resDateList` 에서 유찰 횟수를 세고, 결과가 빈 매각기일을 `d` 로
- `resNote` 를 `special_rights()` 에 넣어 `sp` 를 채운다
- 색인 값과 다르면 **CODEF를 정답으로 채택**하고 `verified:true`, `verifiedAt` 기록, `mnApprox` 는 지운다
- **다만 CODEF 가 '결과 미게시' 로 주는 기일에 대해 우리가 이미 결과를 알고 있으면 그것을 지우지 않는다.** 없다는 것은 데이터가 아니라 데이터의 부재다. apply_codef 가 그 가드를 갖고 있다(2026-09-19 추가) — 사용자가 확인해 준 2026타경3134·2025타경32082 의 유찰이 매일 통째로 지워지고 있었다. 이 가드를 풀지 마라.
- 검증이 끝난 물건의 발굴 안내문('법원 원본 대조 전입니다')은 apply_codef 가 지운다. 2026-09-12 에 검증 완료 228건이 그 문구를 단 채 '법원 확인' 배지와 나란히 나오고 있었다.

**4-e. 색인 재확인 — CODEF 대신 기일 지난 물건의 결과 되짚기 (2026-09-24 사용자 지시 "이렇게라도 진행할수 있게 해줘")**
네이버 웹문서 검색 스니펫에 경매정보 사이트(richgo·경매알리미·보스옥션)가 결과를 적어 둔 경우만 반영한다.
**한쪽 방향으로만 믿는다** — 매각·낙찰·종료, 그리고 저감 계단 검산을 통과한 유찰만 반영하고 '진행중' 신호는 버린다
(색인이 2~3주 늦어 팔린 물건도 진행중으로 나온다). 아무 신호가 없으면 아무것도 바꾸지 않는다. 틀린 매각 표시는
진짜 기회를 목록에서 지운다.
(1) `python3 scripts/index_recheck.py --targets` — 기일이 지난 진행중·미확인 물건을 사건 단위로 40건 골라
    `data/idx-targets.json` 에 쓰고 검색어를 찍는다(대시보드 전송분 매일 → 대구권 → 나머지 사흘마다).
(2) 키가 있으면 `python3 scripts/naver_search.py idx.tsv --idx` (찍힌 검색어를 그대로, display=5) 로 끝낸다 — 그러면 (3) 의
    extract_naver 단계는 건너뛴다. 키가 없으면 찍힌 검색어를 **그대로** `NaverSearch-search_webkr` 로 하나씩 부른다(`display=5`). 검색어 꼴
    `{사건번호} 매각기일 최저입찰가 결과` 를 바꾸지 마라 — 2026-09-24 실측으로 고른 꼴이고, 바꾸면
    `--eval` 부터 다시 해야 한다. 여러 사건을 한 검색에 묶지 마라.
(3) `python3 scripts/extract_naver.py "<DD Mon YYYY — KST 오늘>" idx.tsv` → `python3 scripts/index_recheck.py idx.tsv`
    로 미리 본 뒤 `python3 scripts/index_recheck.py idx.tsv --write`. 신호가 없어도 찾아본 물건에 `idxAt` 이 찍혀
    내일 같은 것만 또 찾지 않는다. **스니펫 TSV 는 커밋하지 마라** — 사이트에 따라 임차인 실명이 가려지지 않은 채 있다.

    36 맞음 · 0 틀림 · 6 판정불가(CODEF 가 결과 미게시로 준 것 — 실제로는 전부 매각이었다).

낙찰가(≈)와 "법원 원본 아님" 안내가 나온다. **이 배지와 문구를 지우지 마라.** 대시보드 갱신 메모에도 "출처 검색 색인 — 법원

**4-b. 선별 등급 (CODEF 뒤에 반드시)**
`python3 scripts/screen_clean.py` — 아파트에 `screen` 을 매긴다. clean(특이사항 없고 유찰 1회 이하) / risk / 미판정. **권리분석이 아니라 '문제가 있을 때 겉으로 드러나는 자국' 이 있나 없나다.** 유찰 횟수도 최저가율도 모르면 clean 에 넣지 마라 — 모르는 것을 걸러진 목록에 넣으면 목록 전체가 거짓말이 된다. CODEF 뒤에 안 돌리면 유치권이 새로 붙은 물건이 계속 '권리 자국 없음' 으로 남는다. 화면 문구에서 "권리분석을 마쳤다는 뜻이 아닙니다" 를 지우지 마라. **예외(2026-10-07 사용자 지시 "대항력이 있어도 권리상 문제가 없는 부분들도 있는데 이것도 포함시켜도 돼")**: 물건비고에 대항력 포기 확약(HUG 등 '우선변제권만 주장, 대항력 포기, 임차권등기 말소 동의')이나 '대항력 없음' 이 법원 문서로 적혀 있으면 대항력은 자국으로 치지 않는다(screenBy 에 '대항력 포기 확약' 이 붙는다). 다른 특이사항·유찰 2회 이상은 그대로 risk 다. 배당으로 전액 회수될지 같은 계산이 필요한 경우는 자동으로 판단하지 않는다.

상세에만 있는 버그를 못 잡는다. 미확인 물건이 '종료' 로 표시되고, 안내문이
"이미 대조된 값입니다" 라고 거짓말하고, 유찰이 0회로 채워지고, 전세 2건으로
'전세가율 200%' 가 찍히던 걸 그렇게 찾았다.
Playwright 에서는 `page.evaluate(() => openDetail('법원|사건번호|물건번호'))` 로 열고
`#view` 의 innerText 를 읽는다. 첫 방문 안내 `#guide` 는 먼저 지운다.

**7. 대구권 푸시 알림 (조건부)**
알림 수단은 **`PushNotification` 하나만 쓴다.**
⛔ **`KakaotalkChat-MemoChat` 은 절대 호출하지 마라.** 이 계정은 여러 사람이 공유해 쓰고 있고 카카오 커넥터 인증자가 누구인지 확인되지 않았다. 사용자가 명시적으로 다시 허용하기 전에는 금지다.

아래 중 **하나라도 해당할 때만** 보낸다:
- 대구권에 **7일 내 매각기일**이 있다
- 대구권에 **새 물건**이 편입됐다
- 대구권 물건의 **상태가 바뀌었다**

메시지 규칙: 200자 이내, 한 줄, 마크다운 금지. 맨 앞에 `[대구권 경매]`. 임박 기일 → 소재지 → 최저가와 감정가 대비 % → 유찰 횟수 순. 특수권리(`sp`)가 있으면 반드시 포함. 대시보드에 보낸 물건이 유찰·변경·매각·종료됐으면 그것을 맨 앞에 쓰고(색인으로 확인한 것은 "(색인)" 을 붙인다), 대장 단지가 새로 자동 등록됐으면 ⭐ 단지명을 그다음에 쓴다. 검증 안 된 유찰 횟수는 쓰지 마라.
