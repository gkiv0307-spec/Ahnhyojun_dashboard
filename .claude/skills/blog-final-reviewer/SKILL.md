# 🧑‍⚖️ 최종검토 직원 스킬

## 역할

2단계(정보검수)에서 걸러졌거나 4단계(SEO검수) 기준 미달인 항목을 최종 검토하고, 발행대기까지 무사히 온 항목은 마지막으로 확인한다.

## 보류 처리

정말 문제가 있으면 "보류" 상태로 확정하고 **구체적인 사유**를 `holdReason`에 남긴다.

- 나쁜 예: "정보 부족", "기준 미달" (무엇이 왜 부족한지 알 수 없음)
- 좋은 예: "출처 기사에서 해당 낙찰가율 수치를 확인할 수 없어 보류", "본문이 1,180자로 최소 분량(1,500자) 기준에 못 미쳐 보류"

이전 단계(정보검수/SEO검수)가 남긴 구체적 메모를 그대로 이어받아서 쓴다 — 이전 단계 메모가 뭉뚱그려져 있다면, 이 단계에서라도 원인을 다시 확인해 구체화한다.

## 발행대기 항목 최종 확인

발행대기까지 온 항목은 마지막 승인 메모만 남기고 그대로 둔다. 단, 다음을 훑어보고 명백한 문제가 있으면 이 단계에서 바로잡는다: 오탈자, 문장이 끊긴 곳, 톤이 갑자기 딱딱해진 부분, 전화번호·CTA 누락.

## 결과 취합 및 업로드 (이 파이프라인 실행의 마지막 책임자)

**이 단계가 그날 파이프라인이 실제로 실행됐다는 증거를 남기는 마지막 지점이다.** 처리한 항목이 하나도 없더라도(아이디어 직원이 소재를 못 찾은 날 포함) 반드시 결과 객체를 만들어 구글드라이브에 업로드한다:

```
{ runAt(지금 ISO), status: "success"|"no_new"|"error", addedCount(items 배열 길이), note(사유 요약, 정상이면 빈 문자열), items: [...] }
```

- 처리한 아이디어가 있으면 `items`에 각 항목을 담는다.
- 처리한 아이디어가 하나도 없으면 `items: []`, `status: "no_new"`, `note`에 아이디어 직원이 남긴 사유를 그대로 옮긴다.
- 중간에 오류가 나서 일부만 처리했다면 `status: "error"`로 표시하고 어디까지 처리했는지 `note`에 남긴다.

**절대 조용히 아무것도 안 올리고 끝내지 않는다.** 과거 이틀 연속 아무 기록도 남기지 않고 파이프라인이 조용히 실패한 적이 있었다 — 이 단계에서 반드시 업로드까지 마쳐야 그런 공백을 막을 수 있다.

업로드 파일명: `ahj_blog_chunk_YYYY-MM-DD.json` (오늘 날짜), parentId: `1ZkIT6DPRGBg8DYu9ezNTEjo6ekUJMvZ4`. 절대 `ahj_dashboard_snapshot.json` 전체 스냅샷을 직접 다운로드·수정·재업로드하지 않는다.

## 마무리 보고

끝나면 오늘 파이프라인이 각 아이디어를 어디까지 처리했는지(발행대기 몇 건, 작성중에 머문 몇 건, 보류 몇 건과 사유, 소재 자체가 없었으면 그 사실도) 한국어로 짧게 요약해서 사용자에게 알린다.
